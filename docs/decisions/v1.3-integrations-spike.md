# v1.3 integrations spike: herdr, T3 Code, Orca

Status: research only. Part of #87 (does not close it). Date: 2026-11-18.

Method: public docs and web summaries only, no hands-on testing, no user data. Nothing below was run against a live herdr or T3 Code. Every "unverified" item needs a hands-on check before its issue is built. Sources: herdr docs (herdr.dev/docs/socket-api, /docs/integrations, /tui/docs/cli-reference/), T3 Code repo and docs (github.com/pingdotgg/t3code: docs/internals/overview.md, docs/user/outside-agents.md), and t3code PRs on the Claude adapter's `settingSources`.

## Recommendation

1. **herdr first.** It is a terminal multiplexer, so Claude Code runs as a normal CLI with the user's hooks. It has a documented socket and CLI with focus commands, and injects pane env vars. Best fit, smallest effort.
2. **Orca: finish the checklist** (sound muting #78, verified landing #79 for the worktree select). Little new work.
3. **T3 Code last, and behind a hands-on spike.** It is an Electron app that drives agents through its own server, probably the Claude Agent SDK. Whether our hooks fire is unproven, and no deep link or focus CLI is documented. Likely "Open T3 Code" (app activate only) at first.

## Common mechanics today

- Host detection: `chippy-hook` walks the process tree to the first regular GUI app (`ProcessTree.walk`), recording pid, bundle id, tty, cwd (`HostInfo`).
- Jump: activate the app, poll for frontmost (`TerminalJump.bringForward`), then an optional host-specific step (Orca: `orca worktree activate --worktree path:<cwd>`).

## herdr

- **What it is:** Rust terminal multiplexer for coding agents. Runs inside a terminal app (it is a TUI, not a GUI app), supports detach and remote sessions.
- **Do hooks reach chippy-hook:** Very likely yes. `herdr integration install claude` adds its own hook entries and a script to the same `settings.json` (version-10 matcher on `SessionStart`), so hooks coexist with ours. Claude runs as an ordinary CLI in a PTY pane. Unverified: that our `SettingsInstaller` entries and herdr's do not clobber each other.
- **Host resolution:** the process walk lands on the terminal app that attached the herdr client (Ghostty, iTerm2, etc.), not on herdr. Detached or remote sessions have no local GUI host at all. So the hook should also forward `HERDR_ENV`, `HERDR_PANE_ID`, `HERDR_WORKSPACE_ID`, `HERDR_TAB_ID`, `HERDR_SOCKET_PATH` (all documented as injected into managed pane processes; ids are opaque, not content).
- **Jump:**
  1. Activate the terminal app (existing path).
  2. Focus inside herdr: `herdr agent focus <pane_id>` (target is a live agent name or the hosting pane id), or `herdr workspace focus <id>` / `herdr tab focus <id>`. Honour `HERDR_SOCKET_PATH` (or `HERDR_SESSION` for named sessions; `--session` is documented for launching herdr only).
  3. Alternative: socket JSON methods `agent.focus`, `workspace.focus`, `tab.focus`.
  - Gap: docs say nothing on raising the OS window; it relies on step 1. If the client is detached, focus succeeds but nothing is visible. Detect with `herdr session list` (unverified output shape).
- **Event surface:** socket `events.subscribe` with `pane.agent_status_changed` (idle, working, blocked, done, unknown), `pane.agent_detected`. Not needed for v1: Claude hooks already give us state. Possible later use: "blocked" for non-Claude agents in herdr (Codex, OpenCode), out of scope for Chippy's Claude focus.
- **Verified landing (#79):** frontmost check covers the terminal app only; pane focus cannot be confirmed except by re-reading `herdr pane list` (unverified).
- **Sound muting (#78):** terminal frontmost is not enough to know the session's pane is visible; accept the terminal-level rule first.
- **PDPA:** all local (Unix socket, CLI). Send only ids. Never use `pane read` (reads terminal content).
- **Risks:** herdr is young (created 2026-03, v0.x), CLI and socket protocol (docs v0.9.5; the "v15" figure in an earlier draft was unverified) may change; forks and mirrored repos exist, pin to ogulcancelik/herdr docs. IDs like `w1:p1` change on cross-workspace moves, so resolve at jump time, not at hook time (or re-list).
- **Effort:** small, about 2-3 days. Hook forwards pane env, `HostInfo` gains an optional `herdr` struct (pure parsing and command building in ChippyCore, tested), label "Open herdr" when `HERDR_ENV=1`, run `herdr agent focus` after activation with a 5s timeout like Orca.

## T3 Code

- **What it is:** open-source (MIT) Electron desktop app, plus web and mobile clients, over a local server that owns provider processes, terminals, git and files. Providers behind adapters: Claude Code, Codex, and others in newer versions. Uses the user's existing provider logins.
- **Do hooks reach chippy-hook:** Unproven. Claude is probably run via the Claude Agent SDK, where filesystem hooks load only when `settingSources` includes the source. t3code PRs show it passing `["user","project","local"]` (earlier `["user","project"]`), which would load `~/.claude/settings.json` hooks, so our hooks may fire. Must be tested: run a thread in T3 Code and watch `events.jsonl` for the session. Also unknown: whether SDK sessions emit the same payload (`PreToolUse` with `permission_request` etc.).
- **Host resolution:** the hook's parent chain would lead to a T3 Code server process (Node child of the Electron app, or a forked helper), then the Electron app. `isGUIHost` should resolve to the T3 Code bundle id (unknown, read from the installed app's Info.plist). Helper processes may be filtered out. If the server runs headless (`t3` CLI, remote), there is no local app.
- **Jump:** No documented focus API, deep link or URL scheme found. Docs mention a Linux URL handler only. What exists: `t3 thread list|show|start|send` CLI (no focus) and an MCP server with OAuth (read/start/message threads). So v1 is app activation only (existing `bringForward`); thread-level focus needs either source reading (`apps/desktop`, `packages/contracts/src/rpc.ts`) for a `t3://` handler, or an upstream feature request.
- **Interaction caveat:** an SDK-driven approval is answered inside T3 Code through its own permission callback. Chippy answering via the `PermissionRequest` hook could race the app's own prompt. Needs a hands-on check, and the fail-open rule (#5 in design rules) must hold.
- **Event surface:** no public push hooks found. MCP/RPC are authenticated, need pairing codes and grants. Do not use them (extra credentials, wider access than needed).
- **Verified landing / muting:** app-level frontmost works the same way as other apps.
- **PDPA:** hooks only; do not touch T3 MCP or its RPC.
- **Risks:** fast-moving (v0.0.x), hook behaviour depends on its adapter internals and may change per release; no jump API; bundle id and process layout unverified.
- **Effort:** spike 1 day (do hooks fire, what is the host chain, bundle id). If yes: small, about 1-2 days for detection, label and activate-only. Exact thread focus: unknown, depends on upstream.

## Review notes (code-review medium on #103, 2026-11-19)

Folded into the build issues #127-#129:

- **Jump order differs by host.** Orca: activate, poll frontmost, then `orca worktree activate`. Terminals (`TerminalJump.open`): a per-terminal osascript step selects the tty window or tab first, then `bringForward`. herdr focus runs after the terminal step, not right after activation.
- **Validate env before use (herdr).** `HERDR_PANE_ID`, `HERDR_SOCKET_PATH` and the other ids come from the process env. Validate strictly (ids match a fixed pattern, socket path is absolute and owned by the user), pass them as arguments after `--`, and never interpolate into a shell. Resolve pane ids at jump time because they go stale.
- **Detached or remote herdr.** If `herdr session list` shows no attached local client, show no "Open herdr" jump (or label it "herdr (not attached)") and never report a landed verdict for pane focus. Output shape unverified.
- **herdr gets a hands-on gate too.** Before the build, spend half a day on: hook coexistence in `settings.json`, `session list` output, `agent focus` against a live pane. The 2-3 day estimate assumes this passes.
- **Orca path.** The hook already records pid and bundle. Resolve the CLI from `NSRunningApplication(pid).bundleURL`, and log plus downgrade the verdict when the CLI is missing or exits non-zero.
