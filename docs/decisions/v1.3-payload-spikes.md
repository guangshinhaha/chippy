# v1.3 payload spikes (#91, #94)

Status: research. Sources: Claude Code hooks reference (https://code.claude.com/docs/en/hooks: ExitPlanMode, PermissionRequest decision control, "Tools that require user interaction") and the permissions page ("Hook approvals in plan mode"), read 2026-11-18. No live capture yet.

## #91 ExitPlanMode

**Payload (documented).** `tool_input` holds `plan` (Markdown string) and `planFilePath` (string). Claude Code injects both from the plan file, because the model's own input is typically empty. `allowedPrompts` is deprecated and ignored. PostToolUse `tool_response` has `plan` and `filePath`. PermissionRequest input is `tool_name` and `tool_input` as in PreToolUse, minus `tool_use_id`, plus optional `permission_suggestions`.

**Can the hook approve or deny?** Yes, per the docs. PermissionRequest response:
`{"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"allow","updatedInput":{...}}}}`
or `behavior:"deny"` with a `message` (and optional `interrupt`). The docs say `AskUserQuestion` and `ExitPlanMode` need `updatedInput` paired with allow; a bare allow is not enough. So Approve must echo the original `tool_input` (plan, planFilePath) as `updatedInput`. Deny with a `message` is the natural "Keep planning" (the message goes to Claude; do not set `interrupt`). The docs spell out the `updatedInput` requirement in detail for PreToolUse; for PermissionRequest they only link to it, so it is assumed to apply.

**Local evidence.** `~/Library/Application Support/Chippy/events.jsonl` holds metadata only (keys: channel, decision, project, tool, ts, wait_ms; content was not read). It has 0 ExitPlanMode rows (14 AskUserQuestion, 10 Bash), so no ExitPlanMode has reached Chippy yet.

**Committed.** `PlanProposal.make(tool:input:)` in ChippyCore, with `PlanProposalTests` and a doc-derived, redacted fixture (inline). It returns nil (generic card) on a missing, empty or non-string plan, strips hidden scalars with `ApprovalIntent.clean`, caps at 2000 chars and keeps only the plan file name. Not wired to any UI.

**Needs a live capture before #91 builds on it:**
1. Does ExitPlanMode reach the PermissionRequest hook at all (not only PreToolUse), and is `plan` populated there? Chippy's relay is installed on PermissionRequest.
2. Does allow with echoed `updatedInput` skip the terminal prompt and leave plan mode as the terminal's Approve does? The terminal offers variants (such as auto-accept edits); Approve may need an `updatedPermissions` `setMode` entry.
3. What does deny plus `message` do to the session (does it stay in plan mode)?
4. Typical plan size, and the Claude Code version that started injecting `plan` (an older one may send an empty `tool_input`; the fallback covers it).

## #94 free text for "Other"

**Finding: feasible in principle, not confirmed.** For AskUserQuestion the hook answers with allow plus `updatedInput`: the original `questions` array plus `answers`, an object mapping each question's text to a string. The docs describe the value as "the selected option label", with multi-select labels joined by commas. The schema is string to string. The docs do not restrict it to the listed labels and do not mention "Other". The terminal's "Other" option presumably stores the typed text in the same field, but that is an inference. Chippy already sends this shape (`NotchModel`, `input["answers"] = answers`).

**Needs a live test before #94:** send `answers` with a string that is not an option label and check that Claude receives it verbatim, for single-select and multi-select (comma-joined, so free text containing a comma may be ambiguous). Also check any length limit, and that the PermissionRequest path (not just PreToolUse) accepts it.

**PDPA.** The typed text is user content: never log it, never write it to events.jsonl.

## #91 built (card wired)

The plan card (`PlanCard`, `--render-plan`) uses `PlanProposal`. Approve echoes `tool_input` as `updatedInput`; Keep planning is deny with a fixed message and no interrupt. "Always" is refused for ExitPlanMode. If the plan is missing or unparsable the generic Allow/Deny card shows (same echo, no Always). If ExitPlanMode never reaches PermissionRequest, no card appears and the terminal prompt works as normal (fail open). Live checks 1 to 4 above are still open.

## #91 review fixes: feature flag and required live checks

The plan card is behind a setting, off by default: status menu "Plan approval card (experimental)", stored in UserDefaults key `planCard`. While off, ExitPlanMode is answered with nothing and the terminal prompt handles it. The same fail-safe applies when the plan is missing or unparsable, or the echoed input is missing: no generic Allow card, the terminal handles it. A plan that Chippy could not show in full (clipped row, dropped rows, scan cap) says "plan continues in the terminal" and the button reads "Approve (partly shown)". The hotkey approves a plan only from an expanded card (or a short plan that is fully shown); there is no "always" key for plans.

**Live checks required before turning the flag on by default:**
1. ExitPlanMode reaches PermissionRequest with `plan` populated.
2. After Approve, the next Edit still prompts in default mode (Approve must not widen permissions).
3. Keep planning stays in plan mode and Claude re-proposes a plan.
4. After the 60s hook timeout the terminal prompt still works.
5. A test plan containing bidi-override and zero-width characters renders cleanly (characters removed, count shown).
